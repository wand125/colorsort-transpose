## 実装

- beamMN と同じ3通りの注ぎ（1個、上の同色の連続、入るだけ全部）、費用は移動玉数。空への全移動・完成単色レーンからの移動・2本目以降の空レーンを除外する。
- g ごとのバケツ、M + aT + bS + dP、f32 の評価と [0,0.02) の同点乱数。既定重みは (0.25,0.5,1)。乱数は seed と親番号・a・b・r から生成し、候補の整列に全順序を与えた。rayon の展開・評価・整列は収集順に依存しない。評価は変わった2レーンの統計と底の連続の上位3本から差分計算し、全盤面を走査する参照式と照合した。
- 重複判定は beamMN と同じレーン順に依存しない64ビットハッシュ。採用済み状態だけを seen に入れる。将来バケツ内の同じハッシュは評価最良の候補を残す。d手先では上位d×W個までに制限する。それまでに新しくseenになるのは最大(d−1)×W個なので、最終的な上位W個を保つ安全な制限である。
- 永続履歴は8バイト（u32親番号とa,b,r）、候補は24バイト。盤面は5ビットの色と高さをu128レーンに格納し、レーン数分だけ連続保持。直近N層を越えた盤面は解放する。盤面ベクトルは必要数を先に確保し、候補の過大な確保も縮小する。seen と履歴は残るため、探索全体のメモリが定数になるわけではない。
- 対応はN=1〜24。`--start` は N+1 レーン・高さ・色ごとの総数を検証。返す手順のレーン番号は入力と同じ。`--upper U` は残りの厳密な改善（g+LB<U）を探索する。ビームで「解なし」は最短性の証明ではない。
- `--lb hd` は lowerbound の h1+d2 を移植。d2 の順番の部分集合DPを等価な最小費用割当て（Hungarian法）に置換した。残すレーンの選択と512組超の緩和は元実装と同じ。
- `--lb j` は証明にあるJの定義を使用し、同型レーン・色の対称性・支配される手の除外・動的下界・閾値判定を実装。指数サイズの密配列やu8飽和は使わず、疎なu32メモ（25万件でクリア）と形ごとの上下界キャッシュ（各スレッド8192件）を使用する。完成済みレーン以外の玉数Aに対しh+D≤2A、J≤2Aなので、2Aが残り予算以下なら計算なしで通す。Jは完成済みを残して残りを全部出す道を使えばこの上界を満たす。これは合格の証明だけで、下界や評価値には使わない。Jの実行可能な道の費用も閾値を通す近道だけに使い、枝刈りの下界には使わない。`--eval-lb` のJは閾値判定を二分探索して正確なJを求める。
- tail は既知手順を replay し、後ろから切り直して短縮を採用・反復。`★ N=… 改善 X -> Y` と出し、出力先の best_N.txt に追記する。tune は既定重み＋一様乱択を小さい幅で比べ、上位を大きい幅で確認する。両スクリプトは逐次実行・最大4スレッド。タイムアウトは自分が作った専用セッションだけを終了する。

## 計測版

v1は差分評価・ローリング盤面・d×W候補保持を備えた版。v2は完成レーンを除いた玉数による安い閾値合格判定を追加した版で、通常Mの評価・候補生成・重複判定・保存形式は同じ。12色の種1でv2を再確認し、1/4スレッドともv1と手順が一致しCPU時間も約10秒だった。

```sh
nice -n 10 env CARGO_TARGET_DIR=beam/target-pour CARGO_BUILD_JOBS=4 cargo test --release --offline --manifest-path beam/Cargo.toml --bin pour -- --nocapture --test-threads=1
env PYTHONDONTWRITEBYTECODE=1 /usr/bin/python3 beam/pour-runs/measure.py distribution
env PYTHONDONTWRITEBYTECODE=1 /usr/bin/python3 beam/pour-runs/measure.py widths

env PYTHONDONTWRITEBYTECODE=1 /usr/bin/python3 tools/pour_tune.py 13 15 --trials 3 --width 300 --confirm-width 2000 --top 1 --timeout 180 --out beam/pour-runs/tune
```

作業ディレクトリはリポジトリ根。計測用Pythonはそのまま起動し、各探索子プロセスに `nice -n 10` を一度だけ適用した。スレッドは1または4、今回の重い計算は同時2本以内。macOS 26.2 (25C56)、arm64、48GiB、論理14CPU。rustc 1.99.0 (b940084d7 2026-09-28)、rayon 1.12.0。既存の他の計算は停止・変更していない。負荷平均は開始時約150、その後250近くになることもあり、壁時計時間には大きな変動がある。壁時計時間はtimeのrealを使う。計測ドライバを検証ビルドの間だけ待たせたケースではJSONのsecondsにその待機が含まれるが、子プロセスを測ったrealには含まれない。RSSは `/usr/bin/time -l` の maximum resident set size（バイト）をMiBに換算する。

以下の各欄は **手数 / 壁時計秒 / CPU秒(user+sys) / 最大RSS MiB**。timeが終了情報を書けなかった中止試行のCPU・RSSは「未取得」、壁時計はドライバの経過秒を「約」で示す。

### メモリの内訳と限界

### 補助計測と結果の範囲

幅を増やすと今回のN=13/15・既定重み・seed=1では手数が短くなった。ビーム幅による単調改善を一般に保証するものではない。

後半解き直しの3か所では329手を更新できなかった。短縮時の採用・反復・best_N.txt追記は別の小さな模擬試験で確認した。重み探索は色数ごとに既定1組＋乱択2組だけで、両方とも既定重みが確認候補に選ばれた。より良い重みは見つからなかったが、既定値が最適という結論ではない。

v2は序盤の不要な下界計算を省いた。例えばN=15・Jのg=50到達は83.7秒から10.9秒になり、v2のg=100到達は66.0秒だった。その先では下界の計算費用が増え、最終的には両版とも180秒で打ち切った。完走速度や解の質の改善は未確認である。

N=16・幅10万・v2を `--max-g 50` で打ち切った補助計測では、壁時計617.26秒、CPU 268.66秒、最大RSS 1396.5MiBだった。これは50手までの保持を調べた値で、完走時の最大メモリや解の存在を示す値ではない。終了コード1はこの手数上限による。

幅30万は仕様の「メモリが許せば」に従う補助計測。N=13の単独試行とN=15の最初の並行試行はOSのメモリ圧迫通知で自分の子プロセスだけを中止した。生ログは `memory-attempts/`（再試行前は同名のルートJSON）、判断履歴は `wide-admission.json`、`wide-memory.jsonl`、`guard13-memory.jsonl`、`retry15-memory.jsonl` に保存する。N=13終了後、圧迫レベルnormalかつ空き指標50%以上が60秒続くことを確認してからN=15を単独再試行した。空き指標は `memory_pressure -Q`、圧迫レベルは `kern.memorystatus_vm_pressure_level` を用いる。
N=15の単独再試行も約6秒後にマシン全体の圧迫レベル2を検出して中止した。幅30万での解なしを意味しない。
